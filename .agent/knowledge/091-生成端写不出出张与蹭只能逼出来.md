# 091 — 生成端写不出「出张」与「蹭」，只能写出**逼出它们的形状**

> ⚠️ **本条为 agent 观察，未经用户确认。** 来源：`docs/research/e2e-trial-01.md` 的端到端试写
> （n=1 首，ロストワンの号哭 13.6）+ 388 官谱的手序统计。
> 它**完全依赖 `tools/chart_analysis/hands.py` 这一套代价模型**——换一套代价模型，结论可能不同。

- **日期**：2026-09-20
- **要点**：出张（知识 **064**）与软级的"蹭"（知识 **011/048/062**）在**读谱端**是可以数的，
  在**写谱端却没有直接对应的操作**——因为本项目的手序是分配器按代价最小算出来的，
  **两只手都够得着时它绝不会主动跨界，也不会主动去蹭**。
  生成端能做的只有**写出逼出它们的形状**：
  ① 用**长条 / 星星钉住一只手的专属键**（左手专属 6/7、右手专属 2/3），逼另一只手跨过去；
  ② 写**侧边双押** `{2,3}` / `{6,7}`（按知识 064 的舒适区定义必然有一只手落在对侧）。
- **详情**：

  1. **试写实证**（e2e-trial-01 §2.3 第 3–4 轮）：把知识 **087 §5** 的对称模板
     `45,,45,,2,3,2` 原样写进一小节，**出张 0 次**——那个形状里两只手都够得着；
     把长条从**共享键** `1h` / `8h` 换到**专属键** `3h`（钉右手）/ `6h`（钉左手）之后，
     出张立刻出现。**长条写在共享键上不会逼出任何东西**，分配器直接把它交给闲着的那只手。
  2. **知识 087 的场景分类是"读谱端"的**：它说"纯单点出张占 30.2%、是最大的一类"——
     那三成是在**官谱既有的那套手序**下数出来的；写谱端**没有办法"指定"这三成**，
     除非把手序由人钉死，而本项目的手序是分配器算的。
     ⇒ **087 的六类里，写谱端可操作的只有类 1/2（被星星/长条钉住，36.2%）和类 5（同刻双押的另一半）。**
  3. **"蹭"同理，而且还有一条更要紧的修正**：e2e-trial-01 §3.4 拿"试写 0 次蹭 vs 那一张官谱 22 次"
     当成写浅了的证据，**这个读法过头了**——388 官谱的软级蹭是
     **中位 1.14 次/千手任务，而且 48% 的官谱一次都没有**。
     ⇒ **「软级蹭 0 次」不是异常，不必为了凑蹭去改谱**；蹭是设计手段（048/062），不是指标。
     真正该看的是**同一张谱里该蹭的地方蹭没蹭**（例如鼓动段防蹭、菱形星星的缝），那是人工复核的事。
  4. **对工具的含义**：检查器的出张 / 蹭清单只能当**复核清单**，
     **不能**当"写谱时的目标值"——把它们当目标会逼出 ③ 那种为了指标而塞的配置，
     正好违反知识 **066**「不以特殊处理的手法为导向」与 **064**「出张轻易不要写」。
  5. **写谱端的正确顺序**（`docs/workflow-sop.md` §5）：先决定"这一段要不要让某只手被钉住"
     （这是**音乐与配置**的决定），出张是它的**副产物**；不要反过来先定"我要几个出张"。

  **证据注脚**：388 谱 `hand-assignment-summary-v2.csv`：软级蹭 中位 1.14 / 千手任务
  （Q1 0.00 / Q3 4.61），**零蹭谱 187/388 = 48.2%**；出张 中位约 21 ‰（定数档 13.0→14.2 依次
  24.3 / 21.4 / 17.3 / 16.9 / 15.0 ‰）。试写 trial-01 终稿出张 6（8.3 ‰）、软级蹭 0。

- **理由**：试写里两次可复现的操作（共享键 → 专属键、加侧边双押）直接改变了出张计数，
  而其他改动（对称模板、密度调整）不改变；蹭那一条由 388 谱的分布直接证伪了 trial-01 的读法。

  ④ "48% 官谱零蹭"这一条是 388 谱的直接计数，**比前三条硬**）。
