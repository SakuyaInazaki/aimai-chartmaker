# 056 — 去量化清理：撤掉 agent 自造的阈值/分档/类名，术语回归用户口径

- **日期**：2026-09-20
- **来源**：**用户 2026-09-20 的五条批评（原话，逐条）**——

  1. 「出张本来是一件很小的事啊，怎么就分档了？」
  2. 「什么是侧边双押位移大的阈值，不是，你怎么能量化来分析这些事情呢？正常写谱谁去特意算这些事情。」
  3. 「什么叫跨共享键的交叉，你又不给我具体展示我怎么知道你这是什么意思。」
  4. （问"纵连 ≤3 tap 是否含 hold / 星星头"时）「你这问的什么问题？只要需要击打按键的不就算吗？」
  5. 「什么叫采七成算不算全采？根本就没有这些词吧，这些词哪来的臆造出来的吗？怎么能量化这些事情呢？」

  **结论（本轮的总口径）**：**制谱判断是谱师的定性判断。agent 自造的阈值 / 分档 /
  合成分 / 分类名不得成为术语、不得进知识库、不得作为问题抛给用户；量化只能留在
  工具内部当诊断输出。**

  第 3 条（「跨共享键的交叉」）由主会话把 `403` / `314` 两段谱例连同左右手表展示给用户、
  等用户裁定，**本轮不处理**。

## 理由

note 055 交付时在 `docs/hand-sequencing.md` §8 挂了 **7 条"待用户裁定"**，
`configs_hand.PENDING_USER_PARAMS` 留了 1 项，`sampling.py` 对外输出 **8 个类名**，
`AGENT.md` 的"待用户拍板"里塞了五个量化问题。用户看到后的反应是上面五条批评：
这些问题**谱师根本不会这么想**，其中大部分的"待裁定"其实是 agent 把自己的操作化
包装成了"需要用户定的参数"。

本轮据此做三件事：**① 该删的阈值/分档删掉；② 自造的类名换回用户的原话词；
③ 待裁定清单只留必须拿谱例问的定性问题。**

## 变更

### 1. 出张不分档（用户批评 1）

- `hands.PARAMS` 的注释删去"单档"说法：**出张 = `is_chuzhang(hand, key)` 这一个布尔判定
  + 一个落点计数**（知识 064）；跨到 6 还是 7、跨多久、跨多频繁都不构成档位。
  `w_chuzhang = 0.90` **保留为搜索内部的代价数字**，但文档不再说"档"、不再列为待裁定。
- `configs_hand.detect_chuzhang` 的 docstring 改写：`chuzhang_min_cross`（几个落点才算一段
  "出张配置"）明确为**内部计数口径**，不是难度分级、不向用户索取。
- `docs/hand-sequencing.md` §3 代价项表 P 行、§3.1、参数默认值表同步。

### 2. 侧边双押删掉阈值框架（用户批评 2）

- **`hands.PARAMS` 删除 `side_sudden_disp` / `side_sudden_gap_sec` / `side_double_redline`**
  三个键；`side_double_events()` 里 `sudden` / `sudden_kind` 两个字段一并删除。
- **红线只保留知识 030 的原话逻辑**：`redline = not guided`——「**突然 = 没有引导**」，
  "突然"**不用数字定义**。引导仍是 A/B（共享键步进）/ C（相邻键对等距轮转）/
  D（临近位置已在这两键上）三型，**全是形状判定**。
- **★ 结果降为复核清单，不再记无理**：`detect_hand_muri` 里的硬级标记 `突然侧边双押`
  **整条删除**。理由写在代码与报告里：去掉阈值后 388 官谱上 685 次侧边双押有 **307 次**
  判不出引导——这说明 agent 归纳的四型**覆盖不全**（用户只给了三个例子），
  把它当自动硬无理等于宣称"官方谱写了 307 次铁律违例"，那是替用户下结论。
  无引导的那些出在 `HandAssignment.side_doubles`，`chart_summary` 新增
  `side_double` / `side_double_unguided` 两个计数。
- 事件里保留 `near_dist` / `gap` / `hand_dist` 作**诊断字段**（定位用），**不参与判定**。
- `configs_hand` 的侧边双押描述同步：标签只剩「有引导（X 型）」/「无引导 —— 请人复核」。
- 验证报告 §V2 降为**方法附录**（标定过程可查，不是规则），并在结论处写明重读。

### 3. 纵连长度按"需要击打按键的 note"数（用户批评 4）

- `hands.py` 新增模块级 `_HIT_KINDS = ("tap", "hold", "star")`；
  `build_tasks` 算 `vrun_len` 时由"只数 `tap`"改成**数所有需要击打按键的 note**
  （tap / hold 的头 / 星星头）。
- 知识 019 补充里记的"待确认项 2"（≤3 是否含 hold / 星星头）**由用户当场答掉**，
  从所有待裁定清单里删除。

### 4. 采音术语回归用户三词（用户批评 5）

- `tools/calibration/sampling.py` **对外只输出三个词**（用户原话：「是采全音、空音还是半采音等等」）：
  **采全音**（把这段音轨的音基本都踩了）/ **半采音**（有选择地只踩一部分）/
  **空音**（该有音的地方留白不踩）；判不出的小节记 `—`（`UNKNOWN`，**不是一类采音方式**）。
- **删除的 agent 自造类名**：`近全采`、`随机半采`、`稀采/空音`、`加花`、`静默`、`混合`。
  其中 `近全采` 正是为了绕开"踩七成算不算全采"而造的，现在并入采全音；
  `半采` / `随机半采` 的区别（踩的是不是重音）降为 `accent` 诊断标记；
  `加花` 降为 `extra_ratio` 诊断字段；`静默` 并入空音；`混合` 改成"不下结论"。
- `THRESHOLDS` 重写成 `full_lo` / `empty_hi` / `empty_min_pool` / `min_pool` 四个切点，
  并在 docstring 里写死：**这是工具内部的诊断口径，不是术语定义，不向用户索取、
  不列为待裁定项、不写进知识库**。
- CLI 默认**不打印** coverage / extra / pool / 挑重音等数字，新增 `--diagnostics` 才出。

## 结果要点（实测）

1. **388 谱基线：去量化没有动"能不能打"。**
   不可行 **141**、绝对无理 **146**、硬无理 **118**、蹭 **859** —— 与 v0.2 **逐行相同**；
   出张落点 5 714 → **5 739**（+0.4%）、出张/slide **0.2322**（不变）；
   侧边双押 669 → **685**（+2.4%），其中**无引导 307**（不变）。
   `突然侧边双押` 这条硬无理**判据已删除**（v0.2 下本来就是 0 次）。
2. **纵连口径影响面很小**：同键连续串（≥2）10 306 → **15 253**，含 hold/星星头的 5 255 个；
   其中 **64** 个由"≤3 免拆"变成按速度线判拆，**4 939** 个旧口径下根本不成串、现在拿到免拆资格。
   三项无理计数一个没变（多数 hold 头本来就把手占到尾，速度项在那儿不是约束）。
3. **采音三词分布**（160 首 / 13 535 小节）：
   **采全音 59.2% / 半采音 24.3% / 空音 8.4% / 判不出 8.1%**。
4. **★ 核心结论在三词口径下原样成立**：「官方谱不是"越难的地方踩得越满"，而是"越难的地方踩得越省"」——
   去环硬度低→高：半采音 **22.0% → 29.2%**、空音 **7.7% → 9.8%**、采全音 **59.9% → 55.8%**，
   而 coverage 几乎不动（0.698 → 0.665）。手序难度那一轴同方向（半采音 23.2% → 26.5%）。
5. **否定结论也复现**：半采音里"踩的是重音"的比例**不随硬度上升**（65.1 / 65.5 / 65.3%）。
6. **"一手被占住 → 半采音"的机制解释在三词下更清楚**：
   半采音占比最高的一批全是一只手被星星/长条钉住的配置（拆弹 59.5%、同起点拍滑 51.4%、
   一笔画 36.6%、双压连续拍滑 36.4%、出张 34.6%、连续拍滑 34.2%…），
   而手型预定的几何配置几乎全是采全音（三角 93.2%、楼梯 95.0%、散点 84.9%、轴 83.6%）。

## 已知风险 / 待办

- **"引导"的四型仍是 agent 按用户三个例子归纳的**，覆盖率未知（388 谱上 307/685 判不出就是证据）。
  要做实只能靠用户补更多引导形态或人工标谱例——**不要再问阈值**。
- 采音三个词之间的界线仍由一个 coverage 切点决定，那是内部口径；
  它影响"某一小节算哪个词"，**不影响**低→高硬度的相对趋势。
