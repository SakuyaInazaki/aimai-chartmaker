## 3. 取材途径

全程**匿名公开接口**，没有用任何登录态：

1. `x/frontend/finger/spi` 拿 `buvid3` / `buvid4`，当 cookie 用；请求一律带浏览器 UA + `Referer: https://www.bilibili.com/video/<BV>`；请求间隔 ≥1 s。
2. `x/web-interface/view` 取元数据（标题、aid/cid、时长、简介）。
3. `x/player/v2` 查 CC 字幕与章节 —— **两条视频 `subtitles` 与 `view_points` 都是空的**，既没有 CC 字幕也没有官方分章。
4. `x/player/playurl`（`fnval=4048`）取 dash 流，只下**视频流**。

⚠️ **清晰度上限 480p**：匿名请求 `qn=64/80` 时接口回 `quality: 64`，但 dash 里实际只给 852×480 和 640×360 两档，720p 及以上要登录。抽帧时用 lanczos 放大到宽 1280 送 OCR（放大本身不增加信息量，但对小字的检测召回确有帮助）。说明栏字号大，480p 已经足够；真正吃分辨率的是谱面截图里的小字。

`yt-dlp` 直接下会 HTTP 412，补上 buvid cookie 后正常；本轮直接走 playurl + curl，没用 yt-dlp。

## 5. 方法

### 抽帧

`ffmpeg` 单次解码，`select='gt(scene,0.1)+not(mod(n,105))'`——**场景切换帧 ∪ 每 3.5 s 固定帧**，再按最小间隔 1.2 s 去重，`scale=1280:-2:flags=lanczos`。
阈值本来按 0.25 设，但这两条视频是连续屏幕录像、没有硬切，0.25 在第二期上**一帧都选不出来**，降到 0.1 才拿到 57 个切换点；主力仍然是固定间隔帧。

### OCR

`rapidocr-onnxruntime` 1.4.4（PP-OCRv4 中文 det+rec），跑在 `.venv-ocr`（py3.11，已加进 `.gitignore`）。
每个文本框记录 `box`、`score`，并按 `x0 ≥ 0.74×宽` 打上 `panel` 标记区分「右侧说明栏」和「左侧画面」——后者主要是曲绘上的曲名曲师和游戏 UI 噪声。

### 文字合并

说明栏的同一段文字会连续停留几十秒，所以把相邻帧按**行集合重叠度 ≥0.6** 归并成段，段内取 OCR 行数最多的一帧当代表（这样说明栏逐行显现时，取到的是最全的那一版）。

### 章节推导

`view_points` 为空，章节**完全从 OCR 推**：说明栏里**单独成行、以冒号结尾的短标题**（或第 0 行的「标题：正文」）当作术语标题，跳过 `曲名/定数/谱师/版本/BPM/特点` 这些元信息标签和 `示例N` 这类通用词；一个标题到下一个标题之间算一个区间，区间内出现的 `曲名：…` 收集为谱例。

### 曲名补全

**这是本轮最要紧的一个坑**：PP-OCRv4 的中文识别模型**会把日文假名整段丢掉**。`ユビキリ`、`セツナトリップ` 这类纯片假名曲名会被识别成空串，`チューリングの跡` 只剩 `の`，`デリヘル呼んだら君が来た` 只剩 `呼君`。
修法不是换模型，而是拿本机 `resource/official-chart/` 的 **388 首官方 ST 谱**当曲名表做模糊匹配：残缺曲名的汉字序列若是候选曲名汉字序列的**子序列**就给高分，再叠 difflib 相似度；纯拉丁曲名要求 ≥0.82（否则会出现 `Splash Dance!!` → `planet dancer` 这种假匹配）。
结果：两期合计 **139 处曲名引用**，**75 处**匹配到官方谱库，去重后覆盖 **66 首**官方谱。匹配分 <0.80 的在 `corrections.md` 里打了 ⚠️，需人工复核；`（库外）` 是本仓库没抓过的曲子，不代表 OCR 错。

## 6. 质量自评（抽 20 帧逐字人工核对）

抽检两期共 20 帧（第二期 8 帧、第三期 12 帧），说明栏文字合计 **1458 字符**，把原图和 OCR 输出逐字对照：

| 类别 | 结果 |
|---|---|
| 中文解说正文、术语标题、`定数/难度/版本/BPM` 等标签与数值 | **零错字**，20 帧全对 |
| 拉丁文词间空格 | 约 6 处丢失（`Beat Per Minute`→`BeatPerMinute`、`Night Fly`→`NightFly` 等），不影响语义 |
| 繁简/标点归一 | 3 处（`最終`→`最终`、`冷凍庫`→`冷凍库`、`・`→`·`） |
| **含日文假名的曲名 / 谱师名** | **8 处里 5 处整段丢失、2 处只剩汉字、1 处正确** |

折算：**已识别出的字符准确率 ≈ 99.9%**（1458 字里只有 1 处漏字 `妄想感傷代償連盟`→`妄想感傷代連盟`），**整体召回 ≈ 97%**（另有约 41 个假名字符被整段丢弃）。
结论：**中文说明文字可以直接当可信材料用；曲名一律以 `corrections.md` 的匹配结果为准，不要信 OCR 原文。**

样本外还发现 1 处术语标题误识：`三叉载` → **`三叉戟`**（同帧正文里「三叉戟」出现多次可证），已纠正。反过来，`双压连续拍滑`（不是「双押」）、`马洼路/马挖路`、`混fr` 经原图确认**都是 UP 主原文**，保留未改。

## 8. 已知局限

1. **曲名是最脆的一环**：假名丢失靠官方谱库兜底，但库里只有 388 首，视频里相当一部分谱例不在库内（`（库外）`），这些曲名只有残缺的 OCR 原文。
2. **章节是自动推导的，没有逐条人工复核**。`现在我们大概知道了BPM、音符…接下来是SLIDE` 这种过渡句也被当成了标题；反过来，如果 UP 主某个术语没有用「标题：」的写法，就会被并进上一条。
3. **清晰度 480p**：说明栏文字够用，但左侧谱面演示里的小字（谱面截图内的 simai、判定细节）基本读不出来。要这部分就得换有登录态的取流途径。
4. **左侧画面文字噪声大**：`screen-text.md` 里 `（画面）` 开头的行混了曲绘文字和 COMBO 数字，当线索可以，别当事实。
5. 第一期 `BV1Lb421p7b5` 没取。
